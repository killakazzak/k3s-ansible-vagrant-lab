# k3s: один master и два worker на Mac

Локальная лаборатория Kubernetes на Ubuntu 24.04: Vagrant создаёт три VM в VirtualBox, Ansible устанавливает k3s. Traefik и ServiceLB включены. По умолчанию один master со встроенным etcd и два workers. Можно добавить master через меню; отказоустойчивость etcd требует минимум трёх master. Rancher устанавливается автоматически через Traefik.

## Меню с цифрами

Из каталога проекта запустите:

```bash
./cluster.sh
```

Выберите действие цифрой:

| Пункт | Действие |
|---|---|
| 1 | Выбрать число master/workers, создать кластер и проверить |
| 2 | Удалить кластер с подтверждением |
| 3 | Показать VM и узлы Kubernetes |
| 4 | Проверить DNS, сеть и Traefik |
| 5 | Добавить worker: ввести имя и свободный IP в подсети |
| 6 | Удалить выбранный worker после drain |
| 7 | Изменить CPU/RAM узла и перезагрузить VM |
| 8 | Выбрать точную версию k3s и пересоздать лабораторию |
| 9 | Добавить master (embedded etcd) |
| 10 | Удалить дополнительный master |
| 0 | Выйти |

**Пункт 8 удаляет данные существующего кластера после подтверждения.** Это пересоздание, не rolling upgrade. Сначала проверяется наличие релиза на GitHub. Для обновления с сохранением данных см. раздел «Изменение версии». При ошибке сети проверка релиза останавливается до удаления VM.

Поддерживается один или несколько master и один или несколько workers. Удаление worker останавливается, если drain не прошёл; автоматического обхода PodDisruptionBudget нет. Данные emptyDir и диска удаляемого worker теряются, локальные PV автоматически не мигрируют. CPU/RAM меняются для выбранного узла; при перезагрузке master API временно недоступен.

Перед изменением YAML меню сохраняет копию в `.cache/menu-backups/`. Эти копии не включают данные приложений. Свободный IP нового worker нужно выбрать с учётом других устройств сети. Если применение завершается ошибкой, настройки остаются записанными — исправьте причину и повторите пункт 1. Настройки версии защищены от неявного обновления существующих VM.

Команды без меню остаются доступны для автоматизации:

## Одна команда

После клонирования репозитория и установки Homebrew и VirtualBox:

```bash
./cluster.sh up --verify   # создать кластер и проверить DNS, сеть и Traefik
./cluster.sh destroy       # удалить VM и данные кластера без подтверждения
```

Повторный `up` применяет настройки к существующему кластеру. Для быстрого запуска без дополнительных сетевых тестов: `./cluster.sh up`. Состояние VM: `./cluster.sh status`. Отдельная проверка: `./cluster.sh verify`.

`destroy` действует на VM этого каталога, после успешного удаления убирает локальный kubeconfig и сохраняет кэш загрузок. Данные на дисках VM теряются. Сохранённые отдельно VM Parallels от предыдущего переноса эта команда не удаляет. Удаление и создание можно повторять; для последующего запуска используйте ту же команду `up`.

## Развёртывание с нуля

Нужен Mac **Apple Silicon**, Homebrew и установленный **VirtualBox 7.2 или новее для Apple Silicon** с доступным `VBoxManage`. Для VM выделяется суммарно 12 ГБ RAM и 6 vCPU; оставьте ресурсы macOS и приложениям. Нужны интернет и свободное место для трёх дисков Ubuntu. Intel Mac этим проектом не поддерживается.

1. Установите Homebrew по https://brew.sh и VirtualBox для Apple Silicon с https://www.virtualbox.org/wiki/Downloads. При запросе macOS разрешите работу сетевых компонентов VirtualBox.
2. Клонируйте репозиторий (для приватного репозитория нужна авторизация GitHub):

```bash
git clone https://github.com/killakazzak/k3s-ansible-vagrant-lab.git
cd k3s-ansible-vagrant-lab
./deploy.sh --verify
```

Скрипт устанавливает отсутствующие Vagrant и Ansible, скачивает совместимый kubectl, создаёт VM, настраивает кластер и сохраняет `kubeconfig` с правами 0600. Homebrew может запросить пароль администратора. Без `--verify` выполняются только проверки готовности узлов, CoreDNS и Traefik.

```bash
./kubectl.sh get nodes -o wide
./kubectl.sh get pods -A
./kubectl.sh -n kube-system get svc traefik
```

Первый запуск требует загрузки Ubuntu box, k3s и контейнерных образов. Для ускорения загрузка k3s идёт одновременно с их запуском, бинарник скачивается один раз на Mac с проверкой SHA256 и копируется на узлы. Повторные запуски используют кэш `.cache/`, `.tools/` и Vagrant box. Фиксированное время первого запуска не гарантируется: оно зависит от сети.

## Настройки

Все основные параметры находятся в `ansible/group_vars/all.yml`; список узлов и IP — в `ansible/inventory.yml`. Vagrant читает эти же файлы.

| Параметр | Назначение |
|---|---|
| `k3s_version` | Точная версия k3s, по умолчанию `v1.36.4+k3s1` |
| `vm_box`, `vm_box_version` | Образ Ubuntu и его версия |
| `vm_cpus`, `vm_memory_mb` | CPU/RAM для server и workers |
| `vm_name_prefix` | Префикс имён VM в VirtualBox |
| `private_network_prefix` | Маска сети VM |
| `pod_subnet`, `service_subnet`, `cluster_dns` | Сети Kubernetes и адрес DNS |
| `disabled_components` | Отключён только metrics-server; Traefik и ServiceLB сохранены |
| `server_taints` | По умолчанию приложения запускаются на workers |
| `dns_servers`, `dns_over_tls` | Внешние DNS и DNS-over-TLS |
| `node_ready_timeout`, `rollout_timeout` | Таймауты готовности |

По умолчанию master: `192.168.58.11`, workers: `192.168.58.21` и `.22`, API: `https://192.168.58.11:6443`. На другом Mac проверьте, что подсеть не пересекается с VPN, LAN и другими VM. При конфликте измените IP всех узлов до первого запуска. Не меняйте сети существующего кластера без пересоздания.

Можно переопределить `vm_cpus` и `vm_memory_mb` для конкретного узла прямо в inventory. Параметры CPU/RAM существующей VM применяйте через `vagrant reload`, затем `./deploy.sh`.

DNS узлов использует systemd-resolved и отдельный listener на private IP. CoreDNS пересылает внешние запросы этому resolver. DNS-over-TLS включён для обхода проблем DNS NAT при VPN; сеть должна пропускать TCP 853. Если это не подходит вашей сети, задайте доступные DNS и `dns_over_tls: false`.

## Traefik

Для Ingress используйте `ingressClassName: traefik`. ServiceLB публикует HTTP/HTTPS на портах 80/443 узлов, где запущены его Pod. Проверяйте адреса через `./kubectl.sh -n kube-system get svc traefik`.

Например, для Ingress с host `app.test`, после создания приложения и Service:

```bash
curl --resolve app.test:80:192.168.58.21 http://app.test/
```

DNS-запись или `/etc/hosts` на Mac должны указывать домен приложения на IP worker. Для собственных приложений TLS и Service настраиваются отдельно; Rancher и его сертификат устанавливаются автоматически. `--verify` создаёт временный nginx на workers и проверяет Ingress, DNS, Service и доступ между Pod, затем удаляет тестовый namespace.

## Повторный запуск и управление

```bash
./deploy.sh                 # применить конфигурацию и проверить готовность
ansible-playbook ansible/verify.yml  # отдельная сетевая проверка
vagrant status
vagrant ssh k3s-master1
vagrant halt                # выключить VM этого проекта
./deploy.sh                 # включить и проверить
```

Добавление worker: добавьте узел с уникальным IP и `vagrant_id` в группу `workers`, затем выполните `./deploy.sh`. Для удаления сначала эвакуируйте приложения (учтите локальные данные):

```bash
./kubectl.sh drain k3s-worker2 --ignore-daemonsets --delete-emptydir-data
vagrant destroy -f k3s-worker2
./kubectl.sh delete node k3s-worker2
```

После этого удалите worker из inventory. Должен остаться хотя бы один worker. `--delete-emptydir-data` разрешает удаление временных данных Pod; перенос persistent volumes требует отдельного плана. Master добавляется пунктом 9 меню; подробности ниже.

## Изменение версии

Для новой лаборатории измените `k3s_version` до первого запуска. Для существующего кластера обычный deploy блокирует смену версии, чтобы не выполнять неподготовленное параллельное обновление.

Самый простой вариант для одноразовой лаборатории — сохранить нужные данные, выполнить `vagrant destroy -f`, изменить версию и снова запустить `./deploy.sh --verify`. **Все данные VM при destroy удаляются.**

Обновление с сохранением данных выполняйте по официальной инструкции https://docs.k3s.io/upgrades/manual: резервная копия datastore и server token, последовательное обновление server, затем workers, с проверкой готовности и совместимости версий. `allow_version_change: true` отключает защиту, но не превращает deploy в безопасный rolling upgrade. Downgrade этим проектом не поддерживается.

## Полное удаление

Из каталога проекта:

```bash
./cluster.sh destroy
```

Команда удаляет VM и их данные. Кэш образов Vagrant и инструментов остаётся для следующего запуска. Другие Vagrant-проекты не затрагиваются.

## Диагностика и секреты

```bash
ansible all -m ping
vagrant ssh k3s-master1 -c 'sudo journalctl -u k3s -n 100 --no-pager'
vagrant ssh k3s-worker1 -c 'sudo journalctl -u k3s-agent -n 100 --no-pager'
./kubectl.sh get events -A --sort-by=.lastTimestamp
```

Лог фоновой загрузки: `.cache/assets.log`. При проблемах VPN проверьте маршруты к private IP, HTTPS к GitHub/реестрам контейнеров и DNS TCP 853. Увеличьте RAM worker при нехватке памяти приложений.

`kubeconfig`, `.vagrant/`, `.cache/`, `.tools/`, ключи и логи исключены из Git. Токен присоединения генерируется k3s и передаётся Ansible с `no_log`; его нельзя публиковать. Kubeconfig предоставляет административный доступ к кластеру.

Проверено на Apple Silicon с VirtualBox 7.2.16, Vagrant 2.4.9 и Ansible 14.3.1: три узла `Ready` на k3s `v1.36.4+k3s1`, CoreDNS, Traefik и ServiceLB работают. Проверки `--verify` прошли: внутренний и внешний DNS, Service, HTTP через Traefik и прямой доступ к Pod на обоих workers. Это проверка на текущем Mac; отдельный чистый Mac ещё не проверялся.

По умолчанию `vm_provider: virtualbox`; отдельный Vagrant-плагин для него не нужен. VM видны в менеджере VirtualBox как `k3s-master1`, `k3s-worker1`, `k3s-worker2`.

Не переключайте провайдер у существующих VM простой заменой переменной: Vagrant хранит привязку провайдера в `.vagrant/`. Используйте отдельный каталог клона и другую подсеть для второго окружения.

Проверка сценариев меню без изменения VM: `ruby tests/menu_test.rb`.


## Добавление master

Пункт **9** в `./cluster.sh`: укажите уникальное имя (например, `k3s-master2`) и свободный IP (`192.168.58.12`). Для третьего master можно использовать `k3s-master3`, `192.168.58.13`. Либо добавьте запись в группу `server` в inventory и запустите `./cluster.sh up --verify`.

Новые master присоединяются последовательно с отдельным server token; worker использует agent token. `k3s_embedded_etcd: true` включает etcd уже на первом master. Если существующий кластер использует SQLite, Ansible временно остановит k3s, сохранит согласованную копию базы и token на VM и в `.cache/migration/<master>/pre-etcd-backup.tar.gz`, затем выполнит штатную миграцию через `cluster-init`. Архив содержит секреты; храните его отдельно перед удалением VM. Это копия datastore, не резервная копия дисков приложений.

**Два master не выдерживают отказ одного:** для etcd нужен кворум. Для отказоустойчивости нужны минимум три master. Дополнительный master по умолчанию требует 2 vCPU и 4 ГБ RAM. Все VM находятся на одном Mac, поэтому отказ самого Mac не покрывается.

Адрес подключения из kubeconfig и первичного присоединения остаётся IP первого master. Балансировщик API/VIP этим проектом не создаётся. Не удаляйте и не переставляйте первый master в inventory; первый master защищён от отдельного удаления; остальные удаляются пунктом 10. Перед добавлением нужен доступ к первому master. Для полного HA доступа к API требуется отдельный балансировщик.

Документация: [k3s — HA со встроенным etcd](https://docs.k3s.io/datastore/ha-embedded).

## Rancher: установка и вход

`rancher_enabled: true` по умолчанию. Ansible автоматически устанавливает cert-manager **v1.21.1** и Rancher **2.15.1** через встроенный Helm controller k3s. Helm на Mac не требуется. Версии, hostname, число реплик, ресурсы и таймаут вынесены в `ansible/group_vars/all.yml`.

Для текущей сети откройте **[Rancher](https://rancher.192.168.58.11.sslip.io)**. По умолчанию hostname вычисляется из IP первого master; после изменения адресов используйте URL из вывода deploy. `sslip.io` требует работающего DNS. При блокировке DNS rebinding задайте собственный домен и настройте его разрешение на Mac и в кластере.

Логин: `admin`. Получить случайный начальный пароль:

```bash
./kubectl.sh -n cattle-system get secret bootstrap-secret \
  -o go-template='{{.data.bootstrapPassword|base64decode}}{{"\n"}}'
```

При первом входе задайте свой пароль администратора. Пароль не записывается в Git. Сертификат выдаётся внутренним CA Rancher: браузер предупредит о недоверенном сертификате. Для лаборатории можно подтвердить исключение; для постоянного использования настройте доверенный сертификат.

По умолчанию одна реплика Rancher для экономии памяти — это не HA Rancher. На master и workers выделено по 4 ГБ RAM. При включённом Rancher меню не разрешает уменьшить RAM ниже 4 ГБ. У уже созданных VM примените новые ресурсы последовательно: `vagrant reload k3s-master1 --no-provision`, `vagrant reload k3s-worker1 --no-provision`, затем `vagrant reload k3s-worker2 --no-provision` и `./cluster.sh up --verify`. Для HA Rancher увеличьте `rancher_replicas` и обеспечьте достаточно ресурсов и независимых узлов.

`rancher_enabled: false` пропускает установку и проверки; уже установленный Rancher этим флагом не удаляется. При смене версии k3s учитывайте совместимость: текущий Rancher рассчитан на 1.34–1.36. Новая лаборатория после `destroy` получает новый пароль и сертификат.

## Выбор количества узлов при создании

Пункт **1** спрашивает количество master (**1–7**) и workers (**1–32**). Enter оставляет текущие значения. Затем показываются будущие имена, IP и общий объём памяти VM; `1` подтверждает запуск, `0` отменяет его.

Если VM ещё нет и количество изменено, inventory генерируется заново: по умолчанию `k3s-master1…N` и `k3s-worker1…N`. IP берутся из текущей подсети, начиная со смещений 11 для master и 21 для workers. Это параметры `menu_node_prefix`, `menu_master_ip_start`, `menu_worker_ip_start`. Диапазоны проверяются на пересечение и выход за пределы подсети. Старый inventory сохраняется в `.cache/menu-backups/`; индивидуальные настройки старых узлов при генерации нового состава не переносятся.

Если VM уже существуют, изменение их количества пунктом 1 блокируется: используйте пункты 5/6/9/10 или сначала удалите кластер пунктом 2. При совпадающем количестве текущие имена, IP и индивидуальные настройки сохраняются, выполняется обычное применение. Неинтерактивная команда `./cluster.sh up --verify` по-прежнему использует готовый inventory и не задаёт вопросов.

## Удаление master

Пункт **10** позволяет выбрать дополнительный master. Последний и первый master защищены: на первом остаются адрес API, адрес Rancher и snapshot. Удаление первого требует отдельного переноса этих адресов; для полной очистки используйте пункт 2.

Перед удалением меню проверяет совпадение etcd-узлов Kubernetes с inventory и готовность всех master. Затем после подтверждения выполняются:

1. Проверка API и сохранение `k3s etcd-snapshot save` на первом master.
2. Drain удаляемого узла без обхода PodDisruptionBudget.
3. Запрос удаления etcd-member через аннотацию `etcd.k3s.cattle.io/remove=true`.
4. Ожидание подтверждающей аннотации `etcd.k3s.cattle.io/removed-node-name` от контроллера k3s.
5. Удаление VM, объекта Node и записи inventory, проверка оставшихся master.

При ошибке snapshot, drain или отсутствии подтверждения etcd VM не удаляется. После запроса etcd операция может завершиться асинхронно даже при таймауте меню: повторный выбор того же master продолжит удаление, если k3s уже подтвердил исключение. Если VM и Node уже удалены, меню позволяет убрать оставшуюся запись inventory. Автоматического возврата удалённого member в etcd нет.

Переход 3 → 2 или 2 → 1 разрешается с предупреждением: такой кластер не переносит отказ одного master. Snapshot находится на первом master в `/var/lib/rancher/k3s/server/db/snapshots/`; он не включает данные приложений и для восстановления требует server token. При полном удалении VM он тоже пропадает.

Механизм подтверждения: [контроллер etcd в k3s](https://github.com/k3s-io/k3s/blob/v1.36.4%2Bk3s1/pkg/etcd/member_controller.go). Порядок действий, отмена и обработка ошибок проверяются командой `ruby tests/menu_test.rb` без удаления живых узлов.

## Vagrant включён в репозиторий

Официальный установщик **Vagrant 2.4.9 для macOS Apple Silicon** находится в [`vendor/vagrant`](vendor/vagrant). При обычном `git clone` он скачивается вместе с проектом; отдельная загрузка с HashiCorp или GitHub Releases при установке не нужна. Размер репозитория увеличен примерно на 54 МБ, Git LFS не требуется.

При создании кластера из меню или через `./cluster.sh up --verify` скрипт проверяет наличие Vagrant. Если его нет, проверяет SHA256 дистрибутива, монтирует DMG, проверяет подпись HashiCorp и запускает системный установщик macOS. Для установки потребуется пароль администратора Mac. Если Vagrant уже установлен, он сохраняется без переустановки и смены версии.

Отдельная установка и проверка:

```bash
./scripts/install-vagrant.sh          # установить только при отсутствии
./scripts/install-vagrant.sh --check  # проверить дистрибутив без установки
```

После установки развёртывание продолжается автоматически. Homebrew по-прежнему нужен для установки отсутствующего Ansible; VirtualBox нужно установить отдельно. Установка самого Vagrant из включённого DMG не требует Homebrew. Этот дистрибутив не подходит для Intel Mac.

При несовпадении SHA256 или подписи установка прекращается. Версия и ожидаемая SHA256 вынесены в `ansible/group_vars/all.yml`; происхождение, официальный список контрольных сумм и лицензия — в `vendor/vagrant`.


## Автоустановка Ansible и ссылки после развёртывания

`./cluster.sh` → пункт 1 или `./cluster.sh up --verify` автоматически проверяет
`ansible` и `ansible-playbook`. Если они отсутствуют, устанавливает Ansible через
Homebrew. Уже установленная версия сохраняется. Homebrew должен быть установлен
заранее. Отдельно проверить/установить: `./scripts/install-ansible.sh`.

В конце успешного развёртывания выводятся адреса с учётом текущего IP первого
master и настроек hostname. Для стандартной сети:

- [Rancher](https://rancher.192.168.58.11.sslip.io) — логин `admin`.
- [Traefik Dashboard](https://traefik.192.168.58.11.sslip.io/dashboard/) — логин `admin` при первом развёртывании.

Получить пароли локально:

```bash
./kubectl.sh -n cattle-system get secret bootstrap-secret -o jsonpath='{.data.bootstrapPassword}' | base64 -d; echo
./kubectl.sh -n kube-system get secret traefik-dashboard-auth -o jsonpath='{.data.password}' | base64 -d; echo
```

Traefik использует HTTPS и отдельный случайный пароль, который сохраняется в
Kubernetes Secret и не меняется при повторном применении. Пароль не попадает в
Git или вывод Ansible. Браузер покажет предупреждение о локальном TLS-сертификате.
Доступ требует подключения Mac к сети VM и разрешения имени через sslip.io.
Путь `/dashboard/` требует завершающий слеш.

Настройки: `traefik_dashboard_enabled`, `traefik_dashboard_hostname`,
`traefik_dashboard_username` в `ansible/group_vars/all.yml`. Имя пользователя
задаётся при создании Secret; изменение переменной не меняет существующие
учётные данные. Отключение dashboard удаляет его маршрут при следующем применении.
Повторно вывести ссылки: `ansible-playbook ansible/access.yml`.

Маршрутизация настроена через [официальный механизм Traefik API/Dashboard](https://doc.traefik.io/traefik/operations/dashboard/)
с `api@internal`; анонимный доступ проверяется на ответ 401.


### Таймаут CoreDNS при первом запуске

Первое скачивание образов может занять несколько минут. Для готовности CoreDNS
и Traefik используется `bootstrap_rollout_timeout: 1200` (секунд); при сбое
Ansible выводит pods и события, включая ошибки загрузки образов и планирования.
После устранения причины продолжите `./cluster.sh up --verify`: удалять VM
или пересоздавать кластер не требуется.

Ссылки и команды получения паролей также доступны в меню: `./cluster.sh` → **11. Ссылки на Rancher и Traefik**. Этот пункт только выводит настройки и не изменяет кластер. Доступность сайтов зависит от состояния кластера.

## Веб-консоль управления

Запуск одной командой из каталога проекта:

```bash
./cluster.sh web
```

Или пункт **12** в `./cluster.sh`. Откройте полный URL, напечатанный в терминале
(`http://127.0.0.1:8765/#token=…`). Ключ создаётся заново при каждом запуске.
Оставьте терминал открытым; при перезапуске сервера откройте новую ссылку и
обновите страницу. Для другого порта: `./cluster.sh web --port 8766`.

Перед стартом проверяются Vagrant и Ansible; отсутствующие устанавливаются теми
же скриптами, что и при обычном развёртывании. Пароль администратора для установки
Vagrant вводится в терминале до старта сервера. Нужны Python 3, Ruby, Homebrew и
VirtualBox согласно требованиям выше. Node.js, npm, pip и сборка фронтенда не нужны.

В интерфейсе доступны:

- Реальное состояние Kubernetes API и Ready-узлов, IP и настроенные CPU/RAM.
- Создание / применение с выбором количества master и workers.
- Добавление и удаление узлов с теми же проверками etcd, что и в меню.
- Изменение CPU/RAM с перезагрузкой выбранной VM.
- Смена версии через пересоздание лаборатории и удаление всего кластера.
- Сетевые проверки и журнал текущей / последней операции.
- Ссылки на Rancher и Traefik с командами получения паролей.

Удаление и смена версии требуют ввести `УДАЛИТЬ`. Первый master и последний
worker защищены от отдельного удаления. Несколько операций одновременно через
веб-консоль не запускаются; второй сервер того же проекта также блокируется.
Не запускайте параллельно изменяющие кластер команды из терминала.

Сервер доступен только на `127.0.0.1`, проверяет Host, Origin и случайный ключ
в заголовке запросов. Не публикуйте его через ingress, туннели или reverse proxy.
Ключ даёт возможность управлять VM от вашего пользователя — не делитесь ссылкой.
Закрытие вкладки не прерывает операцию. Перед Ctrl+C дождитесь её окончания;
журнал хранится в памяти сервера и очищается при его перезапуске.

Проверки API: `python3 -m unittest discover -s tests -p web_test.py -v`.
Проверено в браузере на текущем Mac: статус двух Ready-узлов, реальные ссылки,
запуск сетевой проверки через интерфейс и успешное завершение с журналом.
Удаление VM и пересоздание версии для проверки дизайна не выполнялись.

Повторный выбор пункта **12** или запуск `./cluster.sh web` показывает ссылку на уже работающую консоль и не запускает второй экземпляр. Адрес с ключом хранится в игнорируемом Git файле `.cache/web.lock` с правами 0600.

### Ресурсы и сеть при создании через веб-консоль

В «Создать / применить» задаются число master и workers, CPU, ОЗУ (МБ) и размер
диска (ГБ) **на каждый узел роли**. Значения master и workers настраиваются отдельно.
Диск: 25–2048 ГБ; размер больше 25 ГБ задаётся через
[Vagrant primary disk](https://developer.hashicorp.com/vagrant/docs/disks/usage)
для VirtualBox. Это размер виртуального диска; раздел и файловая система внутри
гостя могут требовать расширения. Увеличенный диск на новой VM в этом изменении
не проверялся; существующие VM для тестирования не пересоздавались.

Выберите существующую подсеть из inventory или новую частную IPv4-сеть с
префиксом, например `192.168.59.0/24` (поддерживаются /16–/28). IP выдаются
автоматически, адрес хоста `.1`, network и broadcast не используются.
Для небольших подсетей применяется компактное размещение адресов с `.2`.
Пересечения с pod/service сетями и нехватка адресов отклоняются.
Подсеть также должна быть разрешена в конфигурации host-only сетей VirtualBox
на вашем Mac; внешние сети/VPN и чужие VM автоматически не сканируются.

В форме добавления master или worker поле IP можно оставить пустым — будет
выбран незанятый в inventory адрес текущей сети. IP также можно указать вручную.
Новая сеть выбирается для всего нового кластера, не для отдельного узла.

Если VM уже существуют, изменение сети, диска или состава через форму создания
блокируется до удаления кластера. Для CPU/ОЗУ существующего узла используйте
«Настроить», для состава — добавление/удаление отдельных узлов.
Проверки планирования без создания VM: `ruby tests/creation_test.rb`.

Формы **«＋ Master»** и **«＋ Worker»** также содержат CPU (1–32), ОЗУ
(МБ, от 4096 при включённом Rancher) и диск (25–2048 ГБ). Значения по умолчанию
подставляются из первого узла соответствующей роли; выбранные ресурсы сохраняются
в inventory индивидуально для нового узла. Пустой IP включает автоматическое
назначение адреса. После обновления кода перезагрузите страницу браузера.

В карточках Rancher и Traefik кнопка **«Пароль»** показывает логин и готовый
пароль из Kubernetes Secret. Пароль запрашивается только при нажатии через
авторизованный локальный API, не кэшируется HTTP и убирается из окна при закрытии.
Для Rancher показывается **первоначальный bootstrap-пароль**: после смены пароля
в Rancher он может уже не подходить. Новый пароль Rancher эта кнопка не восстанавливает.

## Несколько независимых кластеров

Вверху веб-консоли находится выбор кластера. `default` — исходный проект.
Нажмите **«＋ Новый кластер»**, задайте имя (например `lab2`) и отдельную частную
подсеть /24 (например `192.168.59.0/24`). Затем откроется форма числа узлов и
ресурсов; подтвердите развёртывание. Можно держать два и более кластера, если
Mac хватает CPU, RAM и места. Изменяющие операции через консоль выполняются по одной.

Каждый дополнительный кластер хранится в `.clusters/<имя>/`: отдельные inventory,
настройки, `.vagrant`, kubeconfig и кэши. Новые ВМ имеют собственный префикс имён.
Сети профилей не должны пересекаться; проверяется также пересечение с pod/service
сетями при создании. Ссылки и пароли запрашиваются для выбранного кластера.
Каталог `.clusters/` исключён из Git. Дистрибутив Vagrant используется общий.
Профиль получает копию скриптов на момент создания; последующие обновления
основного репозитория автоматически в старые профили не копируются.

**«Удалить выбранный кластер»** удаляет только его ВМ и kubeconfig после ввода
`УДАЛИТЬ`; конфигурация профиля сохраняется для повторного развёртывания.
Если ВМ уже удалены, интерфейс показывает **«Не создан»**, а таблица — только
сохранённую конфигурацию. Меню терминала отдельно сообщает фактическое состояние
ВМ и не выдаёт inventory за работающий кластер.

Команды для созданного дополнительного профиля из корня репозитория:

```bash
./cluster.sh --cluster lab2 status
./cluster.sh --cluster lab2 menu
./cluster.sh --cluster lab2 up --verify
./cluster.sh --cluster lab2 destroy
```

Проверено: изоляция конфигураций, путей Vagrant и kubeconfig, запрет пересечения
сетей и статус удалённых ВМ (12 автоматических тестов). В браузере проверены
панель выбора, форма нового профиля и «Не создан» на текущем удалённом кластере.
Два полных кластера в рамках проверки не разворачивались.

### Очистка после удаления

После успешного удаления ВМ через меню или веб-консоль активный inventory
очищается. До удаления сохраняются inventory и настройки в
`.cache/deleted-clusters/<время>/` (каталог 0700, файлы 0600). При ошибке удаления
список узлов не очищается. Версия k3s, ресурсы по умолчанию и последняя сеть
сохраняются; сеть записывается в `private_network_cidr`.

Пустой кластер показывает пустой список узлов. Создайте его заново через пункт 1
меню или «Создать / применить» в браузере: по умолчанию предлагаются 1 master и
2 workers. После удаления старые имена узлов не восстанавливаются автоматически.
Смена версии через пересоздание отдельно сохраняет выбранную топологию.
Эта процедура заменяет прежнее поведение, при котором inventory сохранялся активным.

### Имена кластеров и узлов

Основной профиль использует префикс `k8s-cluster1` при следующем создании. В форме «Новый кластер» оставьте имя пустым: автоматически выбирается первый свободный номер, начиная с `k8s-cluster1`. Если основной кластер существует, номер 1 занят им Узлы получают имена `k8s-cluster2-master1`, `k8s-cluster2-worker1`. При добавлении узла предлагается первое свободное имя с префиксом выбранного кластера. Для новых профилей имена VM в VirtualBox совпадают с именами узлов. Существующие VM и Kubernetes Node автоматически не переименовываются; новый шаблон основного кластера применяется при пересоздании.

В строке состояния отображается приблизительное оставшееся время по медиане последних пяти успешных операций с тем же действием и параметрами (имена и адреса сети не учитываются). История хранится локально в `.cache/durations.json`. При первом запуске прогноз ещё недоступен; если операция длится дольше прогноза, интерфейс сообщает об этом и продолжает показывать текущий этап до завершения скрипта.

Кнопка **«Скачать kubeconfig»** вверху веб-консоли скачивает файл подключения выбранного кластера: например, `k8s-cluster2-kubeconfig.yaml`. Использование: `kubectl --kubeconfig ~/Downloads/k8s-cluster2-kubeconfig.yaml get nodes`. Скачивание доступно в авторизованной сессии после появления файла при развёртывании. Для подключения с другого компьютера нужна доступность сети VM; скачивание файла само по себе не открывает сетевой доступ.

В терминальном меню `./cluster.sh` пункт **13 — Список кластеров** показывает сохранённые профили, их каталоги и наличие kubeconfig. Пункт **14 — Подключиться через kubectl** предлагает выбрать кластер, печатает полную команду `kubectl --kubeconfig=/абсолютный/путь/kubeconfig get nodes -o wide` и команду `export KUBECONFIG=...`, затем проверяет доступность узлов. Экспорт нужно выполнить в своём терминале; меню не меняет окружение родительской оболочки.

При запуске `./cluster.sh` ссылка на работающую веб-консоль выводится перед меню, включая токен входа. Если сервер остановлен, вместо устаревшей ссылки выводится команда запуска веб-консоли в другом терминале.

Веб-консоль обновляет список кластеров и состояние узлов каждые 15 секунд, когда вкладка видима и форма редактирования закрыта. После завершения операции данные обновляются сразу. Профили с пустым inventory скрываются из списка; настройки и резервные копии остаются на диске. Если все кластеры удалены, список показывает «Нет кластеров — создайте новый».

Во время развёртывания можно выбрать другой кластер в выпадающем списке, смотреть его состояние, ссылки и скачивать kubeconfig. Операция продолжает выполняться для исходного кластера; журнал подписан его именем. Изменяющие операции остаются последовательными — следующую можно запустить после завершения текущей.

Пункты 13 и 14 терминального меню также скрывают профили с пустым inventory после удаления. Когда список пуст, выбор кластера для kubectl не предлагается.

### Образ Ubuntu с диском 25 ГБ

Новые кластеры используют `k8s-lab/ubuntu-24.04-25gb`, размер диска по умолчанию — 25 ГБ на master и worker. При первом `./deploy.sh` образ собирается локально скриптом `./scripts/build-box-25.sh`: загружается Packer 1.14.2 с проверкой SHA256, исходники Bento фиксированной ревизии и ISO Ubuntu с проверкой контрольной суммы. Создаётся временная VM с диском 25 ГБ, после установки Ubuntu она упаковывается в Vagrant box. Нужны интернет, VirtualBox, около 4 ГБ свободной RAM для сборки и дополнительное место для ISO и промежуточного образа. Первое развёртывание дольше; следующие используют готовый локальный box. 25 ГБ — ёмкость диска каждого узла, а не требование свободного места для всего кластера.

Готовый box и кэш не включаются в Git. Для отдельной сборки: `./scripts/build-box-25.sh`. Старый Bento-образ имеет диск 64 ГБ и не может быть уменьшен настройкой Vagrant. Существующие профили и VM сохраняют свои размеры; для диска 25 ГБ создайте новый кластер с новым образом. Новый образ предназначен для VirtualBox на Apple Silicon.

Проверено локально: новый box добавлен в Vagrant, тестовая VM успешно запущена через `vagrant up`, работают SSH и sudo; `lsblk` показывает диск 26 843 545 600 байт (25 ГиБ). Тестовые VM после проверки удалены. Полный Kubernetes-кластер на новом образе отдельно не разворачивался.

«Новый кластер» открывает одну форму с именем, сетью, количеством узлов и ресурсами. До нажатия «Подтвердить» профиль не записывается, узлы и резервирование сети не появляются. Отмена закрывает форму без изменений. При подтверждении параметры проверяются, затем профиль сохраняется и запускается развёртывание.

Автоматическое имя использует первый свободный номер среди существующих кластеров. После удаления всех кластеров нумерация снова начинается с `k8s-cluster1`. Пустые профили не занимают номера; при повторном использовании имени их настройки и история переносятся в `.cache/archived-profiles/`. Профили с оставшимися VM или нечитаемой конфигурацией не переиспользуются.

### Полноценный терминал в веб-консоли

Под журналом нажмите **Открыть терминал**. Запускается локальная zsh на Mac,
а KUBECONFIG автоматически указывает на выбранный кластер.
Работают Tab (команды, параметры, имена ресурсов Kubernetes), ↑/↓ (история),
Ctrl+C, конвейеры, `kubectl exec -it`, `logs -f` и `port-forward`.
Например: `kubectl get pods -A` или `kubectl exec -it deploy/nginx-demo -n nginx-demo -- sh`.
Shift+Tab позволяет выйти из терминала к кнопкам страницы.

У каждого кластера отдельная сессия; переключение сохраняет запущенную команду.
**Закрыть сессию** завершает оболочку и текущую команду. Обновление страницы
или остановка сервера закрывает сессии. После обрыва связи сессия очищается
через 30 минут без обращений. Максимум 8 сессий; последние 256 КБ вывода
хранятся в памяти сервера. История не записывается на диск.
Пользовательская `.zshrc` не загружается; дополнения kubectl включаются отдельно.

Это терминал Mac с правами текущего пользователя, не SSH в VM.
Адрес с токеном даёт доступ к терминалу; сервер слушает только 127.0.0.1
и проверяет Origin и токен. Не публикуйте его через ingress.
Xterm.js 5.5.0 включён в `web/vendor` с MIT-лицензией; CDN/npm для запуска не нужны.

### Запуск и остановка веб-сервера из меню

В `./cluster.sh`: **12 — запустить веб-сервер / показать ссылку**,
**15 — остановить веб-сервер**. Запуск идёт в фоне и сразу возвращает меню.
Повторный запуск показывает ссылку существующего сервера.
Остановка закрывает встроенные терминальные сессии; VM продолжают работать.
Во время развёртывания или другой операции остановка отклоняется.

Команды без меню: `./cluster.sh web-start`, `./cluster.sh web-stop`,
`./cluster.sh web-status`. Для запуска на другом порту: `./cluster.sh web-start --port 8766`.
`./cluster.sh web` по-прежнему запускает сервер в текущем терминале до Ctrl+C.

### Карта кластера

Раздел «Карта кластера» показывает путь: пользователь → Ingress / IngressRoute
Traefik → Service → Pod → Master или Worker. Выберите маршрут и нажмите элемент
для подробностей. Связи Service/Pod берутся из EndpointSlice с учётом namespace;
пунктирные линии показывают размещение подов на узлах.
Внутренний api@internal Traefik отображается отдельно от Kubernetes Service.
Обновление каждые 15 секунд; на узких экранах прокрутите карту вправо.
Это схема конфигурации и готовности, а не трассировка реальных HTTP-запросов.

Карта показывает владельца Pod по ownerReferences: Deployment (через ReplicaSet),
DaemonSet, StatefulSet, Job/CronJob и другие контроллеры. Pod без контроллера
и статический Pod отмечаются отдельно. В описании маршрута указан тип Service:
ClusterIP, NodePort, LoadBalancer или ExternalName; Headless отмечается дополнительно.

## Каталог приложений и dev/test-стенды

В разделе **Приложения и стенды** выбранный вверху кластер определяет, куда
выполняются все действия. Изменяющие операции используют общий журнал и блокировку:
создание кластера и применение приложения не запускаются одновременно.

### 1. Каталог

Нажмите **＋ Приложение**. Доступны Nginx, PostgreSQL 18.6, Redis 8.10.1 и произвольный
образ. Укажите имя, namespace, точный тег/digest образа, порт контейнера, реплики,
CPU в millicores и RAM в MiB. Лимиты CPU/RAM вдвое больше запросов.
Для HTTP укажите префикс `web` (получится `web.<IP-master>.sslip.io`) или полный
hostname; пустое поле создаёт только внутренний Service.

Nginx/custom используют Deployment. PostgreSQL/Redis — StatefulSet, PVC и
Headless Service плюс обычный ClusterIP для клиентов. Нужен default StorageClass
(в k3s — local-path). Размер PVC задаётся в GiB. По умолчанию база одиночная:
несколько реплик здесь не являются репликацией PostgreSQL/Redis.
PostgreSQL создаёт пользователя `app`, базу `app` и случайный пароль в Secret
`<имя>-auth`, ключ `password`. Пароли не попадают в журнал и шаблоны.
Redis доступен без пароля только через ClusterIP в лабораторном кластере.
Подключения, переменные окружения и SecretRef вашего custom-приложения при необходимости
добавляйте через kubectl: универсальной автоматической настройки приложения нет.

Каталог не перезаписывает одноимённые существующие ресурсы или занятый hostname.
При ошибке проверки ресурсы остаются для диагностики; успешная часть набора не удаляется.

### 2. Диагностика

Нажмите Pod на карте либо **Pods / логи** в карточке приложения. Доступны состояние
контейнеров, Ready, число рестартов, причины ожидания/завершения, события и последние
150 строк логов (до 30 КБ), включая предыдущий запуск. **Терминал контейнера**
выполняет `kubectl exec -it ... -- sh` в локальной консоли. В образах без `sh`
используйте подходящий инструмент отладки вручную.

### 3. Шаблоны

Заполните приложение, нажмите **Добавить текущее в набор**, измените имя/тип для
следующего и повторите. Укажите имя шаблона и нажмите **Сохранить набор как шаблон**.
Шаблон можно развернуть на другом выбранном кластере в новом namespace.
К префиксам URL добавляются namespace и IP этого кластера (web-dev.IP.sslip.io); полные hostname сохраняются.
Сохраняются параметры приложений, а не данные PVC или содержимое Secrets.
Для изменения сохранённого набора нажмите его карточку → **Редактировать**.
Можно переименовать шаблон, добавить или удалить приложения и изменить их параметры.
**Сохранить изменения** обновляет только шаблон; развёртывание запускается отдельно.
Отмена закрывает редактор без сохранения.
Шаблоны хранятся локально в `.cache/app-templates.json`, не включаются в Git.

### 4. Остановка и возобновление

**Остановить VM** выполняет штатный `vagrant halt` только для существующих VM профиля.
**Возобновить VM** — `vagrant up --no-provision` для выбранных узлов; готовность Kubernetes отображается отдельно.
Диски сохраняются; удалённые VM не создаются этой операцией.
До подтверждения показаны суммарные CPU, RAM и логическая ёмкость дисков.
В CLI: пункты **16/17** или `./cluster.sh stand-stop` / `./cluster.sh stand-start`.
Не запускайте CLI-операции одновременно с изменениями из веб-консоли.

### 5. Версии и откат

**Версия / реплики** меняет образ выбранного контейнера и количество реплик;
`0` останавливает приложение без удаления PVC. **Откат** возвращает предыдущую
ревизию шаблона Pod, но не данные базы и не число реплик. Системные namespace скрыты.
Для баз каталога откат образа запрещён, смена major PostgreSQL и Redis запрещена:
обновления major и восстановление данных требуют отдельной процедуры.
История ревизий сохраняется Kubernetes (для новых приложений до 5 ревизий).

### 6. Проверки

После создания автоматически проверяются rollout, DNS и соединение с Service
из временного Pod. Nginx/HTTP проверяются HTTP-запросом, PostgreSQL — `SELECT 1`
с подключением через Service, Redis — `PING`. При HTTP Ingress URL дополнительно
проверяется с Mac. Тестовый Pod удаляется после проверки. Образы проверок требуют
доступа к registry. Кнопка **Проверить** повторяет проверки; у внешних приложений
ожидается Service с тем же именем, используется его первый порт.
Эти smoke-проверки подтверждают инфраструктурное подключение, а не бизнес-логику
произвольного приложения или его миграции базы данных.


### Kafka, RabbitMQ и выбор VM

В «Остановить VM» / «Возобновить VM» отметьте нужные узлы флажками.
Пустой выбор не запускает операцию. Отображается сумма ресурсов выбранных VM.
Запуск отдельной VM не ожидает готовности всего Kubernetes: если master выключен,
API недоступен, даже когда worker уже работает. Диски сохраняются.

В каталоге доступны также:

- **Kafka** — `apache/kafka:4.3.1`, один StatefulSet/PVC, KRaft broker + controller,
  без ZooKeeper. По умолчанию 1024 MiB RAM и 500m CPU, порт 9092.
  Bootstrap server: `<имя>.<namespace>.svc.cluster.local:9092`.
  PLAINTEXT без аутентификации, доступ внутри лабораторного кластера;
  HTTP Ingress для протокола Kafka не создаётся. Проверка — запрос метаданных брокера.
- **RabbitMQ** — `rabbitmq:4.3.5-management`, один StatefulSet/PVC,
  512 MiB RAM и 500m CPU, AMQP 5672. Поле URL публикует веб-панель на порту 15672
  через Traefik. Логин `app`, случайный пароль в Secret `<имя>-auth`, ключ `password`.
  Получить пароль: `kubectl -n <namespace> get secret <имя>-auth -o jsonpath='{.data.password}' | base64 -d; echo`.
  Проверяются DNS, соединение с сервисом, `rabbitmq-diagnostics check_running` и URL панели.

Это одиночные брокеры для dev/test; число реплик ограничено одним. Данные хранятся
в PVC. Автоматический откат образа брокера запрещён из-за совместимости данных.
Шаблоны стендов поддерживают оба приложения, пароли в шаблоны не записываются.
Документация: [Apache Kafka](https://kafka.apache.org/40/configuration/broker-configs/),
[RabbitMQ Management](https://www.rabbitmq.com/docs/management).

PostgreSQL по умолчанию: `postgres:18.6-alpine`. PVC монтируется в `/var/lib/postgresql`,
PGDATA — `/var/lib/postgresql/18/docker`. Старые шаблоны PostgreSQL 17 сохраняют
прежний путь данных; переход с 17 на 18 требует отдельной миграции.

### Карта Pod и панели приложений

Раздел **Pod на узлах** показывает все namespace, включая системные. Поиск работает
по имени, namespace и образам. Pod сгруппированы по master/worker; Pending без узла
показаны отдельно. Нажмите Pod, чтобы увидеть владельца, IP, возраст по времени
создания, образы, requests/limits, PVC, QoS, состояния и рестарты, затем открыть
логи/события/терминал. Обновление каждые 15 секунд. Ресурсы — настройки Pod,
а не измерение фактического потребления CPU/RAM.

При новом развёртывании из каталога автоматически создаются:

- PostgreSQL → **pgAdmin** (`dpage/pgadmin4:9.17`), сервер базы уже добавлен.
  Пароль подключения к базе возьмите в карточке приложения.
- Redis → **Redis Insight** (`redis/redisinsight:2.70.0`), подключение преднастроено.
- Kafka → **AKHQ** (`tchiotludo/akhq:0.25.1`), подключение преднастроено.
- RabbitMQ → встроенная **Management UI**, URL создаётся и при пустом поле URL.
- Nginx / свой HTTP-образ → ссылка на сам сайт при заданном hostname;
  универсальная панель администратора произвольного образа не устанавливается.

Ссылки появляются прямо в карточке. **Ссылки и пароли** показывает логины,
пароли с кнопками показа/копирования и внутренний DNS приложения. Учётные данные
генерируются отдельно для каждого приложения и хранятся в Kubernetes Secrets.
В журнал и шаблоны пароли не записываются. Redis Insight и AKHQ защищены BasicAuth
на Ingress, pgAdmin и RabbitMQ используют собственную форму входа.
Панели публикуются по HTTP в локальной сети лаборатории. Для внешней публикации
настройте HTTPS. Настройки сессий панелей используют emptyDir и могут сбрасываться
при замене Pod; данные самих баз и брокеров остаются в PVC.
Панели требуют дополнительно по 256 MiB RAM (лимит 1 GiB) и 100m CPU.
Ранее установленные приложения автоматически не изменяются.

### Удаление приложения и результат проверки

В карточке приложения доступна кнопка **Удалить**. Требуется ввести `УДАЛИТЬ`.
По умолчанию сохраняются PVC и пароль базы; отдельный выбор позволяет удалить
также данные без восстановления. У приложения каталога удаляются принадлежащие
ему workload, Service, Ingress, веб-панель, её настройки и учётные данные.
Namespace и соседние приложения сохраняются. Для внешних приложений удаляется
только workload (и PVC при явном выборе); внешние Service/Ingress сохраняются.
Сохранённый PVC защищён от случайной перезаписи при повторном создании приложения.

Кнопка **Проверить** показывает последний результат: зелёный — успешно, красный —
ошибка, жёлтый — проверка выполняется. Текст и время доступны независимо от цвета.
Результаты хранятся локально в `.cache/app-checks.json` каждого профиля, привязаны
к UID и generation workload, переживают обновление страницы и сбрасываются при
изменении конфигурации или пересоздании приложения. Это результат последней
проверки, а не непрерывный мониторинг доступности.


### PVC: информация и подключение

Раздел **Persistent Volume Claims** показывает namespace, размер, статус,
StorageClass, режим доступа, связанный PV и использующие диск Pod.
Список обновляется автоматически. В каталоге доступен выбор:

- **Создать новый PVC** — размер из поля «Постоянный диск»; используется default
  StorageClass кластера. Для StatefulSet создаётся volumeClaimTemplate.
- **Подключить существующий PVC** — только Bound Filesystem PVC в том же
  namespace, не используемый Pod. Диск не очищается и не пересоздаётся.
- **Без PVC** — для Nginx и произвольного образа.

Для Nginx/своего образа укажите путь монтирования (по умолчанию `/data`).
Приложение с общим PVC ограничено одной репликой. Для PostgreSQL/RabbitMQ с прежним
диском укажите существующий Secret с ключом `password` и прежним паролем
пользователя `app`. Версия, формат и путь данных должны соответствовать образу;
автоматической миграции данных нет. У баз используются стандартные пути каталога.

Подключённый существующий PVC и его пароль не удаляются при удалении приложения,
даже с выбором удаления данных. Новый PVC удаляется только по явному выбору.
Шаблон с существующим PVC требует такой же PVC в namespace целевого кластера.

### Компактный обзор ресурсов

Pods, PVC и Secrets объединены в раздел **Ресурсы кластера** с вкладками,
общими namespace/поиском и счётчиками. По умолчанию показана таблица с прокруткой.
У Pods можно переключиться на карту размещения. Нажатие на имя открывает
подробности справа (на узком экране — под списком), без ухода со страницы.
В подробностях Pod доступны переход к PVC и логи/события/терминал;
из PVC — обратно к использующему его Pod. Значения Secrets в обзор не выводятся.

### Текущая утилизация узлов

В таблице узлов показаны CPU (ядра и процент от capacity), RAM (working set
в GiB и процент физической памяти) и заполнение корневой файловой системы VM.
Источник — kubelet `/stats/summary` через Kubernetes API, Metrics Server не нужен.
Обновление каждые 15 секунд; время берётся из самого измерения. При недоступности
узла показывается отсутствие метрик, а не нулевая нагрузка. Измерения старше
двух минут помечаются устаревшими. Это ресурсы VM целиком, включая системные
процессы; диск не показывает заполнение каждого отдельного PVC или диска Mac.
